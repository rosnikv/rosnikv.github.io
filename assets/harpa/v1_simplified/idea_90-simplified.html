ID: idea_90-simplified

simple-medical-qa-rag

Hypothesis

Augmenting Retrieval-Augmented Generation with simple structured medical term relationships will improve the factual accuracy of language models in medical question answering tasks compared to using standard RAG alone.

Elements

  • Independent variable: Augmentation of RAG with structured medical term relationships
  • Dependent variable: Factual accuracy of language model responses
  • Comparison groups: Standard RAG vs. RAG augmented with structured medical term relationships
  • Baseline/control: Standard RAG implementation
  • Context/setting: Medical question answering tasks with a focused subset of medical topics
  • Assumptions: The integration of simple structured relationships is feasible with limited resources
  • Relationship type: Causation
  • Population: Language models used in medical question answering
  • Timeframe: Short-term experiment (1-2 months)
  • Measurement method: Accuracy on medical QA benchmark dataset

Description

This research explores a simplified approach to improving medical question answering using Retrieval-Augmented Generation (RAG). Instead of integrating complex knowledge graphs, the project focuses on enhancing RAG with structured medical information in the form of simple term relationships extracted from medical dictionaries or ontologies. The study will compare a baseline RAG system against an enhanced RAG system that incorporates these structured relationships as additional context during retrieval. This approach addresses the challenge of factual accuracy in medical QA systems while being implementable with limited resources and technical expertise. The research aims to demonstrate that even simple structured information can significantly improve the accuracy of medical QA systems when properly integrated with RAG.

Operationalization

Please implement a medical question-answering experiment comparing standard RAG with RAG enhanced by medical term relationships. The experiment should be implemented in three pilot phases (MINI_PILOT, PILOT, FULL_EXPERIMENT), controlled by a global PILOT_MODE variable.

Phase Specifications:
1. MINI_PILOT:
- Use 10 medical questions from the training set
- Use 5 medical documents for the corpus
- Run time: ~5-10 minutes
- Purpose: Code verification and basic debugging

2. PILOT:
- Use 100 medical questions (70 train, 30 dev)
- Use 25 medical documents
- Run time: ~1-2 hours
- Purpose: Verify approach viability

3. FULL_EXPERIMENT (not to be run automatically):
- Use full dataset (train/dev/test split)
- Use full document corpus
- Purpose: Final evaluation

Implementation Requirements:

1. Data Loading:
- Use Huggingface Datasets to load a medical QA dataset (e.g., MedQA or BioASQ subset)
- Filter for questions about a specific medical domain (e.g., cardiovascular)
- Split into train/dev/test according to pilot phase

2. Document Corpus:
- Load medical documents relevant to the chosen domain
- Create document embeddings using a consistent embedding model
- Store in a simple vector database (e.g., FAISS)

3. Term Relationship Extraction:
- Use WordNet/NLTK to extract medical term relationships
- For each medical term identified:
* Get synonyms, hypernyms, and definitions
* Store in a simple lookup dictionary

4. RAG Implementation:
a. Baseline (Standard RAG):
- For each question:
* Get question embedding
* Retrieve top-k relevant documents
* Format prompt with question and retrieved documents
* Generate answer using gpt-4o-mini

b. Enhanced RAG:
- For each question:
* Get question embedding
* Retrieve top-k relevant documents
* Identify medical terms in question
* Add term relationships to context
* Format enhanced prompt
* Generate answer using gpt-4o-mini

5. Evaluation:
- Compare generated answers with reference answers
- Calculate accuracy, precision, recall
- Perform bootstrap resampling to test significance
- Generate plots comparing performance
- Save detailed logs of all operations

Required Outputs:
1. CSV file with per-question results
2. JSON file with aggregate metrics
3. PDF plots of performance comparisons
4. Detailed log file of operations
5. Example outputs (at least 10) showing system differences

Special Instructions:
- Use gpt-4o-mini for all LLM operations
- Log all operations using the logger
- Stop after PILOT phase for human verification
- Save all intermediate results
- Include error handling for API failures

Success Criteria:
1. Code runs without errors in MINI_PILOT
2. Both RAG systems generate valid answers
3. Evaluation metrics are properly calculated
4. Statistical comparison is performed correctly
5. All required outputs are generated
