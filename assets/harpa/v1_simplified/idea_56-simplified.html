Hypothesis

Incorporating explicit entity boundary information in prompts will improve precision and recall in zero-shot entity typing compared to standard prompting without boundary information.

Elements

  • Independent variable: Presence and type of entity boundary information in prompts
  • Dependent variable: Precision and recall in zero-shot entity typing
  • Comparison groups: Standard prompts vs. prompts with explicit entity boundary information
  • Baseline/control: Standard prompts without explicit entity boundary information
  • Context/setting: Zero-shot entity typing with pre-trained language models
  • Assumptions: The boundary information will have a measurable impact on typing accuracy
  • Relationship type: Causation
  • Population: English text from news articles in FIGER dataset
  • Timeframe: Not applicable
  • Measurement method: Precision, recall, and F1 metrics

Description

This research investigates how providing clear entity boundary information in prompts affects zero-shot entity typing performance. Rather than implementing complex Copy-Generation Networks, this study focuses on a simpler approach: enhancing prompts with explicit entity boundary markers and comparing different boundary representation strategies. The research will evaluate how these enhanced prompts improve a pre-trained language model's ability to identify entity types without specific training examples. This approach addresses a key challenge in entity typing—boundary ambiguity—while being implementable with limited computational resources and programming experience.

Implementation Design

# Entity Boundary Prompting for Zero-Shot Entity Typing

## Experiment Overview
This experiment will investigate whether explicitly marking entity boundaries in prompts improves zero-shot entity typing performance. You will implement two prompting strategies and compare their performance on a subset of the FIGER dataset.

## Implementation Details

### 1. Data Preparation
- Download the FIGER dataset (a simplified version is available on GitHub).
- Extract 500 sentences containing entity mentions for testing (100 for the pilot).
- Create a list of entity types to predict. For the pilot, use these 5 types: PERSON, LOCATION, ORGANIZATION, EVENT, PRODUCT.
- For each sentence, extract the entity mention and its gold standard type.

### 2. Prompt Design
Implement two prompt designs:

**Baseline Prompt (without boundary information):**
```
Identify the type of the entity in the following sentence. Choose from these types: PERSON, LOCATION, ORGANIZATION, EVENT, PRODUCT.

Sentence: {sentence}
Entity: {entity}
Entity type:
```

**Enhanced Prompt (with boundary information):**
```
Identify the type of the entity in the following sentence. Choose from these types: PERSON, LOCATION, ORGANIZATION, EVENT, PRODUCT.

Sentence: {sentence_with_markers}
Entity: {entity}
Entity type:
```

Where `{sentence_with_markers}` replaces the entity mention with a marked version, e.g., "Apple announced new products" becomes "[ENTITY]Apple[/ENTITY] announced new products".

### 3. Model Implementation
- Use the OpenAI API to access GPT-3.5-Turbo.
- Create a function that takes a sentence and entity as input, constructs both prompt versions, and queries the model.
- Extract the predicted entity type from the model's response.
- Implement error handling for API failures and unexpected responses.

### 4. Evaluation
- For each test example, record:
- The sentence and entity
- The gold standard entity type
- The predicted type from the baseline prompt
- The predicted type from the enhanced prompt
- Calculate precision, recall, and F1 score for both prompting strategies.
- Perform error analysis by categorizing the types of errors made by each approach.

### 5. Extensions (if time permits)
- Test different boundary marking styles (e.g., "<entity>Apple</entity>" vs "[ENTITY]Apple[/ENTITY]" vs "Apple (ENTITY)").
- Experiment with providing examples in the prompt (few-shot learning).
- Test on more entity types beyond the initial 5.

## Output Generation
- Save all prompts, responses, and predictions to a CSV file.
- Generate a results table showing precision, recall, and F1 for both approaches.
- Create visualizations comparing the performance across different entity types.
- Write a brief report (2-3 pages) describing the methodology, results, and conclusions.

## Evaluation Reporting
- Report overall precision, recall, and F1 scores for both approaches.
- Conduct statistical significance testing using McNemar's test to determine if the difference in performance is significant.
- Analyze which entity types benefit most from the boundary information.
- Provide examples of cases where the enhanced prompt succeeded but the baseline failed, and vice versa.

Operationalization

# Entity Boundary Prompting Experiment

Implement an experiment to test whether explicit entity boundary markers in prompts improve zero-shot entity typing performance. The experiment should be implemented in three pilot stages (MINI_PILOT, PILOT, FULL_EXPERIMENT), with increasing scale.

## Dataset
Use the Huggingface Datasets API to load the FIGER dataset. If not available on Huggingface, fall back to the GitHub version.

For each pilot stage:
- MINI_PILOT: 10 examples
- PILOT: 100 examples
- FULL_EXPERIMENT: 500 examples

## Entity Types
Use these 5 entity types: PERSON, LOCATION, ORGANIZATION, EVENT, PRODUCT

## Prompt Templates

Baseline (without boundaries):
```
Identify the type of the entity in this sentence. Choose from: PERSON, LOCATION, ORGANIZATION, EVENT, PRODUCT.

Sentence: {sentence}
Entity: {entity}
Type:
```

Experimental (with boundaries):
```
Identify the type of the entity in this sentence. Choose from: PERSON, LOCATION, ORGANIZATION, EVENT, PRODUCT.

Sentence: {sentence_with_markers}
Entity: {entity}
Type:
```

Where {sentence_with_markers} adds [ENTITY] markers, e.g.: "[ENTITY]Apple[/ENTITY] announced new products"

## Implementation Steps

1. Create a global PILOT_MODE variable that can be set to 'MINI_PILOT', 'PILOT', or 'FULL_EXPERIMENT'

2. Data Loading:
- Load appropriate number of examples based on PILOT_MODE
- Split into 70% train, 15% dev, 15% test for PILOT and FULL_EXPERIMENT
- For MINI_PILOT, use all examples for quick testing

3. Experiment Implementation:
- For each example:
a. Generate both baseline and experimental prompts
b. Query gpt-4o-mini using the LLM proxy server
c. Extract predicted entity type from response
d. Log full prompt and response
e. Calculate running accuracy

4. Evaluation:
- Calculate precision, recall, F1 for each approach
- Use bootstrap resampling to test for significant differences
- Generate plots comparing performance across entity types
- Log all results, including example-level predictions

## Required Outputs

1. Results file (CSV) containing:
- Example ID
- Original sentence
- Entity
- Gold label
- Baseline prediction
- Experimental prediction
- Correctness flags

2. Summary statistics:
- Overall precision, recall, F1
- Per-entity-type metrics
- Bootstrap test results

3. Visualizations:
- Bar plot comparing overall metrics
- Per-entity-type performance comparison

## Error Handling

- Implement robust error handling for API calls
- Log all errors with full context
- Skip failed examples but continue experiment
- Report error rate in final results

## Execution Order

1. Run MINI_PILOT first (10 examples)
2. If successful, run PILOT (100 examples)
3. Stop after PILOT - await human verification before FULL_EXPERIMENT

## Success Criteria

1. MINI_PILOT success:
- Code runs without errors
- All components (data loading, API calls, evaluation) work
- Results format is correct

2. PILOT success:
- Reasonable performance metrics
- Statistical testing works
- Error rate < 5%
- Clear performance difference between conditions

Note: Use gpt-4o-mini for all LLM calls as specified in the conditioning instructions.
