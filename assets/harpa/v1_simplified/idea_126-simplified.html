SRL-Enhanced-QA

Hypothesis

Applying Semantic Role Labeling as a preprocessing step will significantly improve language model performance on multi-hop question answering tasks compared to the same model without SRL preprocessing.

Elements

  • Independent variable: Application of Semantic Role Labeling preprocessing
  • Dependent variable: Performance on multi-hop question answering tasks (accuracy, F1 score)
  • Comparison groups: Same language model with and without SRL preprocessing
  • Baseline/control: Language model without SRL preprocessing
  • Context/setting: Multi-hop question answering tasks using HotpotQA dataset
  • Assumptions: SRL preprocessing will enhance semantic understanding without requiring complex graph restructuring
  • Relationship type: Causation
  • Population: Pre-trained language models (BERT-base or RoBERTa-base)
  • Timeframe: Not applicable
  • Measurement method: Accuracy, F1 score, and performance gap between single-hop and multi-hop questions

Description

This research explores how Semantic Role Labeling (SRL) can improve language models' performance on multi-hop question answering tasks. Multi-hop QA requires models to connect information across multiple steps, which many models struggle with (the 'compositionality gap'). By applying SRL preprocessing to identify predicate-argument structures in both questions and context passages, we hypothesize that models will better understand the semantic relationships between entities, leading to improved performance on multi-hop questions. This approach provides a structured semantic representation that helps bridge the compositionality gap without requiring complex graph restructuring techniques. The research will evaluate whether this simpler semantic enhancement significantly improves performance on standard multi-hop QA benchmarks compared to baseline models without SRL preprocessing.

Operationalization

Please create an experiment to evaluate whether Semantic Role Labeling (SRL) preprocessing improves language model performance on multi-hop question answering tasks. The experiment should be implemented in three pilot modes (MINI_PILOT, PILOT, FULL_EXPERIMENT), controlled by a global PILOT_MODE variable.

1. Dataset Preparation:
- Use the Huggingface Datasets API to load the HotpotQA dataset
- For MINI_PILOT: Use 10 questions from training set
- For PILOT: Use 200 questions from training set, 50 from dev set
- For FULL_EXPERIMENT: Use full dataset (but don't implement this yet)

2. Model Setup:
- Use gpt-4o-mini as the base model for both conditions
- Baseline condition: Direct input of questions and context
- Experimental condition: Add SRL preprocessing before input

3. SRL Preprocessing:
- For each question and context passage:
- Use gpt-4o-mini to identify predicates and arguments
- Format: "[PRED:verb] [ARG0:subject] [ARG1:object] ..."
- Example: "[PRED:wrote] [ARG0:Shakespeare] [ARG1:Hamlet]"

4. Evaluation Process:
- For each pilot mode:
a. Process questions through both baseline and SRL-enhanced conditions
b. Calculate metrics:
- Accuracy and F1 score
- Separate scores for single-hop vs multi-hop questions
- Compositionality gap (difference in performance)
c. Generate plots comparing performance
d. Perform bootstrap resampling to test significance

5. Specific Settings:
MINI_PILOT:
- 10 questions (5 single-hop, 5 multi-hop)
- 2 epochs
- Log every prediction
- Expected runtime: 5-10 minutes

PILOT:
- 200 training questions, 50 dev questions
- 3 epochs
- Log aggregate metrics every 20 questions
- Expected runtime: 1-2 hours

FULL_EXPERIMENT (don't implement yet):
- Full dataset
- 5 epochs
- Log aggregate metrics every 1000 questions

6. Required Outputs:
- Save all predictions in JSON format
- Generate performance comparison plots
- Statistical significance test results
- Log file with detailed execution information

7. Success Criteria:
- Code runs without errors
- All metrics are calculated correctly
- Statistical tests are performed properly
- Results are properly logged and visualized

IMPORTANT NOTES:
1. Start with MINI_PILOT mode
2. Only proceed to PILOT if MINI_PILOT succeeds
3. Stop after PILOT - do not implement FULL_EXPERIMENT
4. Use gpt-4o-mini for all LLM operations
5. Log all steps and intermediate results
6. Save all model outputs and evaluation metrics
