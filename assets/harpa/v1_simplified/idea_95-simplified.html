ID: idea_95-simplified

simplified-evidence-retrieval

Hypothesis

Implementing a simple contrastive learning approach with a pre-trained BERT model will improve precision and recall in evidence retrieval for multi-hop question answering tasks on a subset of the HotpotQA dataset compared to a standard BM25 retrieval baseline.

Elements

  • Independent variable: Retrieval method (contrastive learning with BERT vs. BM25 baseline)
  • Dependent variable: Precision and recall in evidence retrieval
  • Comparison groups: Contrastive learning with BERT vs. BM25 baseline
  • Baseline/control: BM25 retrieval algorithm
  • Context/setting: Multi-hop question answering tasks on a subset of the HotpotQA dataset
  • Assumptions: The implementation of the contrastive learning approach will be feasible with limited computational resources
  • Relationship type: Causation
  • Population: A subset of tasks within the HotpotQA dataset (e.g., 1000 examples)
  • Timeframe: Not specified
  • Measurement method: Precision, recall, and F1 metrics

Description

This research explores a simplified approach to improving evidence retrieval for multi-hop question answering by implementing a basic contrastive learning technique on top of pre-trained language models. Rather than developing a complex Entity-centered Fusion Encoder, this project focuses on using existing BERT-based models with a straightforward contrastive learning objective to distinguish between relevant and irrelevant evidence passages. The study will use a subset of the HotpotQA dataset to evaluate whether this lightweight approach can improve precision and recall in evidence retrieval compared to a standard retrieval baseline. This simplified approach makes the research more accessible while still addressing the important challenge of improving evidence retrieval for multi-hop question answering.

Operationalization

# Evidence Retrieval with Contrastive Learning - Pilot Experiment

Implement a pilot experiment to evaluate contrastive learning for evidence retrieval in multi-hop QA. The experiment should support three modes (PILOT_MODE): MINI_PILOT, PILOT, and FULL_EXPERIMENT.

## Data Requirements
For each mode:
- MINI_PILOT: 10 training examples, 5 test examples from HotpotQA
- PILOT: 100 training examples, 50 test examples from HotpotQA
- FULL_EXPERIMENT: 1000 training examples, 200 test examples from HotpotQA

## Implementation Steps

1. Setup and Configuration:
- Create a PILOT_MODE variable defaulting to 'MINI_PILOT'
- Initialize logging using the Logger/Debugging codeblock
- Log all major steps, warnings, and errors

2. Data Loading:
- Use Huggingface Datasets to load HotpotQA
- For each example, extract:
* Question
* Supporting facts (positive examples)
* Non-supporting facts (negative examples)
- Balance dataset (1:3 ratio of positive to negative examples)

3. Model Implementation:
- BM25 Baseline:
* Implement using rank_bm25
* Retrieve top-5 passages for MINI_PILOT, top-10 for others

- Contrastive Model:
* Use gpt-4o-mini through the LLM proxy server
* Training parameters by mode:
- MINI_PILOT: 2 epochs, batch_size=4
- PILOT: 3 epochs, batch_size=8
- FULL_EXPERIMENT: 5 epochs, batch_size=16

4. Evaluation:
- Calculate metrics:
* Precision@k (k=5 for MINI_PILOT, k=10 for others)
* Recall@k
* F1 score
- Use bootstrap resampling for statistical testing
- Create visualization comparing metrics

5. Output and Analysis:
- Save results to JSON file including:
* Configuration (PILOT_MODE, parameters)
* Performance metrics
* Statistical test results
- Generate plots using MatPlotLib showing:
* Performance comparison between models
* Learning curves (for PILOT and FULL_EXPERIMENT)

## Execution Flow
1. Start with MINI_PILOT mode
2. If successful, proceed to PILOT mode
3. Stop after PILOT mode completion
4. Wait for human verification before FULL_EXPERIMENT

## Success Criteria
- MINI_PILOT: Code runs without errors, produces basic metrics
- PILOT: Shows clear performance difference between methods
- Statistical significance testing shows p < 0.05

## Required Outputs
1. Logged execution details
2. Performance metrics JSON
3. Comparison plots
4. Trained model checkpoints

## Error Handling
- Log all errors with stack traces
- Implement graceful fallback for LLM API failures
- Save partial results if execution fails

Note: The experiment should first run in MINI_PILOT mode. Only proceed to PILOT mode if MINI_PILOT succeeds. Do not run FULL_EXPERIMENT mode - this requires human verification of pilot results first.
