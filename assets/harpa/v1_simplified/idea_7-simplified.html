ID: idea_7-simplified

prompt-persona-logic

Hypothesis

Task-specific prompt personas will improve GPT-3.5-turbo's logic puzzle solving performance compared to static general personas or no personas, as measured by task accuracy and completion time.

Elements

  • Independent variable: Prompt-based persona configuration (task-specific, static general, or none)
  • Dependent variable: Logic puzzle solving performance
  • Comparison groups: Task-specific persona vs. static general persona vs. no persona
  • Baseline/control: No persona configuration
  • Context/setting: Logic puzzles of varying difficulty
  • Assumptions: Prompt-based personas can influence model behavior without modifying model activations
  • Relationship type: Causation
  • Population: GPT-3.5-turbo model instances
  • Timeframe: Single-session experiments
  • Measurement method: Task accuracy and completion time

Description

This research investigates how different prompt-based persona configurations affect GPT-3.5-turbo's performance on logic puzzles. Rather than implementing complex Role Vector embeddings that modify model activations, this study focuses on comparing different prompt-based persona approaches: (1) a static persona that remains constant throughout the interaction, (2) a task-specific persona tailored to logic puzzles, and (3) a baseline with no explicit persona. The research aims to determine which prompt-based approach yields better performance on a standardized set of logic puzzles, measuring both accuracy and completion time. This simplified approach maintains the core investigation of how model behavior can be guided through personas, but uses accessible prompt engineering techniques rather than requiring direct model modification.

Operationalization

Please create an experiment to investigate how different prompt-based persona configurations affect LLM performance on logic puzzles. The experiment should use gpt-4o-mini as the base model.

The experiment should have three modes controlled by a PILOT_MODE variable:

MINI_PILOT:
- Use 3 logic puzzles (1 easy, 1 medium, 1 hard)
- Run each puzzle once with each prompt configuration
- Maximum 5 minutes total runtime
- Use training set puzzles only

PILOT:
- Use 9 logic puzzles (3 easy, 3 medium, 3 hard)
- Run each puzzle twice with each prompt configuration
- Maximum 30 minutes total runtime
- Use training set puzzles for parameter tuning, dev set for evaluation

FULL_EXPERIMENT:
- Use 30 logic puzzles (10 easy, 10 medium, 10 hard)
- Run each puzzle three times with each prompt configuration
- No runtime restriction
- Use training set for tuning, dev set for validation, test set for final evaluation

Implementation Steps:

1. Dataset Generation:
- Use the Data Generation with LLM codeblock to create logic puzzles
- For each puzzle, generate:
* Problem statement
* Step-by-step solution
* Final answer
* Difficulty rating (easy/medium/hard)
- Store in JSON format

2. Prompt Configurations:
Implement three configurations:
a) Task-specific: "You are LogicSolverGPT, an expert in solving logic puzzles. You excel at breaking down problems step-by-step, identifying constraints, and methodically working through possible solutions until you find the correct answer."
b) Static general: "You are a helpful assistant."
c) Baseline: No persona (empty string)

3. Evaluation Process:
- For each puzzle-prompt combination:
* Send to gpt-4o-mini
* Record full response
* Extract:
- Final answer
- Number of reasoning steps
- Token count
- Response time
- Presence of logical errors

4. Data Collection:
Store results in CSV with columns:
- puzzle_id
- difficulty
- prompt_type
- run_number
- correct (boolean)
- token_count
- response_time_seconds
- reasoning_steps_count
- has_logical_errors
- full_response

5. Analysis:
- Calculate per-configuration:
* Overall accuracy
* Accuracy by difficulty
* Mean token count
* Mean response time
- Use bootstrap resampling to compare configurations
- Generate plots:
* Accuracy by configuration and difficulty
* Token count distributions
* Response time distributions

6. Required Outputs:
- CSV file with all raw results
- PDF with analysis plots
- JSON file with statistical test results
- Log file with full execution details

IMPORTANT NOTES:
1. Start with MINI_PILOT mode
2. If successful, proceed to PILOT mode
3. Stop after PILOT mode - await human verification before FULL_EXPERIMENT
4. Use consistent random seeds for reproducibility
5. Implement robust error handling and logging
6. Save all intermediate results

Success Criteria:
1. All modes complete without errors
2. Data collection matches specified format
3. Statistical analyses are properly conducted
4. Visualizations are clear and informative
5. Results are reproducible with same random seed
