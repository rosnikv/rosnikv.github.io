ID: idea_117-simplified

simple-biomedical-rag-comparison

Hypothesis

A two-step retrieval approach will improve F1-score in biomedical question-answering tasks compared to a single-time retrieval approach.

Elements

  • Independent variable: Retrieval approach (single-time vs. two-step)
  • Dependent variable: F1-score in biomedical question-answering tasks
  • Comparison groups: Single-time retrieval vs. Two-step retrieval
  • Baseline/control: Single-time retrieval approach
  • Context/setting: Biomedical question-answering tasks using a subset of BioASQ dataset
  • Assumptions: The two-step retrieval approach can be effectively implemented with basic programming skills and limited computational resources
  • Relationship type: causation
  • Population: Biomedical questions from a selected subset of BioASQ
  • Timeframe: Not specified
  • Measurement method: F1-score

Description

This research investigates the effectiveness of a simple multi-time retrieval approach compared to single-time retrieval in biomedical question-answering tasks. Rather than implementing a full modular RAG system with multiple external components, this study focuses on comparing a basic two-step retrieval process against the conventional single-step retrieval method. The two-step approach will first retrieve documents based on the initial query, then perform a second retrieval based on the refined context. This simplified approach aims to determine whether even a basic implementation of multi-time retrieval can improve performance on biomedical QA tasks, providing insights into the potential benefits of more complex dynamic retrieval systems while being feasible for implementation with limited resources.

Operationalization

Please create an experiment comparing single-time vs. two-step retrieval approaches for biomedical question answering, with the following specifications:

1. PILOT FRAMEWORK
Implement a PILOT_MODE variable with three settings:
- MINI_PILOT: Use 10 factoid questions from BioASQ training set
- PILOT: Use 100 factoid questions from BioASQ training set for training, 50 from dev set for evaluation
- FULL_EXPERIMENT: Use full dataset (but do not implement this mode yet)

2. DATA PREPARATION
- Use the Huggingface Datasets API to load BioASQ dataset
- Filter for factoid questions only
- For each question, store: question_id, question_text, gold_answer, relevant_documents

3. IMPLEMENTATION
Create two retrieval approaches:

A. Baseline (Single-time Retrieval):
- Input: question_text
- Use gpt-4o-mini to generate embeddings for question and documents
- Retrieve top-5 most similar documents
- Pass question + retrieved documents to gpt-4o-mini for answer generation

B. Experimental (Two-step Retrieval):
- Input: question_text
- First retrieval: Same as baseline
- Use gpt-4o-mini to generate refined query from question + initial documents
- Second retrieval: Get top-5 documents using refined query
- Pass question + final retrieved documents to gpt-4o-mini for answer generation

4. EVALUATION
- Calculate F1-score for each question's answer vs gold_answer
- Calculate retrieval precision/recall using relevant_documents
- Use bootstrap resampling to compare baseline vs experimental performance
- Generate plots comparing F1-scores and retrieval metrics

5. OUTPUT
Create three files:
- results.csv: question_id, question, gold_answer, baseline_answer, experimental_answer, baseline_f1, experimental_f1
- retrieval_stats.csv: question_id, baseline_precision, baseline_recall, experimental_precision, experimental_recall
- summary.txt: Average metrics, statistical test results, key findings

6. EXECUTION ORDER
1. Run MINI_PILOT first (10 questions)
2. If successful, run PILOT (100 train + 50 dev questions)
3. Stop before FULL_EXPERIMENT for human verification

7. LOGGING
- Log all major steps, including:
* Dataset loading/filtering
* Each retrieval operation
* Answer generation
* Evaluation calculations
- Log any errors or warnings
- Log timing information for key operations

8. ERROR HANDLING
- Implement robust error handling for API calls
- Cache intermediate results where possible
- Include progress tracking for long-running operations

Please implement this experiment using the specified codeblocks, focusing first on the MINI_PILOT to verify functionality.
